## 1. Project Overview

**AutoServe AI** is a GenAI copilot for an automotive **after-sales service network**: dealer workshops plus an
OEM warranty desk. It uses LLMs (EURI / Gemini / Groq via OpenAI-compatible APIs), RAG, LangChain, and a LangGraph multi-agent workflow to:

- answer owner questions from the **owner's manual**, with citations (warning lights, maintenance, tyres, EV charging)
- book service appointments through conversation and open a **Repair Order (RO)**
- decode the **VIN**, pull service history, and match open **recalls** and **TSBs**
- give technicians a **diagnostic copilot**: DTC + symptoms → cited procedures + ranked hypotheses
- extract structured data from uploaded ROs, parts invoices, and service records
- check **warranty eligibility** with deterministic rules from the warranty booklet
- build estimates and warranty claims from the **labour-time guide** + parts price list (deterministic maths)
- flag anomalies **for review**: odometer rollback, duplicate claims, labour above flat-rate, repeat repairs
- report the real RO / claim status from the database
- prepare evidence packs for the **service advisor** and **warranty administrator, who make the binding decisions**

## 2. Prime Directive — "AI assists, certified humans decide" (A1)

| AI MAY | AI MUST NEVER |
|---|---|
| Explain manual / service-manual / warranty text it retrieved, with citations | Invent torque values, fluid specs, part numbers, DTC meanings, labour times, or warranty terms |
| Rank diagnostic hypotheses with evidence and a confidence | Authorise a repair, approve a warranty claim, or approve a customer estimate |
| Draft an estimate using the deterministic calculator | Produce any price, labour hour, or amount that the calculator did not compute |
| Flag anomalies "for review" with evidence | Call anything "fraud" or accuse a dealer, technician, or customer |
| Tell an owner to stop safely and contact service when the manual says so | Say a vehicle is "safe to drive" when a safety-critical warning is present |
| Recommend escalation to a certified technician | Give step-by-step instructions to disable/bypass safety systems (airbags, ABS, ADAS, immobiliser, emissions controls) |
| Give EV high-voltage information from the manual | Give DIY high-voltage repair steps to owners (route to a certified HV technician) |
| Report the status stored in the DB | Report a status, date, or ETA that is not in the DB |

**Safety-critical systems** (always trigger escalation + safety banner): brakes, steering, airbags/SRS,
tyres/wheels, seat belts, fuel leaks, EV high-voltage battery/thermal events, ADAS camera/radar calibration.
The banner text, escalation wording, and keyword list are defined in `rules/55-automotive-safety.md`.
Banners have two tiers (OD-01). An **informational** banner + escalation appears for any safety-critical topic. The **stop-safely**
banner appears only when the cited manual chunk requires it, or the owner reports an active warning or symptom.

## 3. Roles (RBAC) (A2)

| Role | Can |
|---|---|
| `vehicle_owner` | Chat, manual Q&A, book service, view own vehicles/ROs/status, approve/decline own estimates, upload documents to own ROs (service_record, odometer_photo, inspection_photo only — OD-07) |
| `service_advisor` | Check in vehicles, manage ROs, edit extracted fields, send estimates to owners, close ROs, cancel ROs (reason required), record owner's verbal consent (note required) |
| `technician` | Diagnostic copilot, record findings + test results, record labour time and parts used |
| `warranty_admin` | Warranty review queue, edit claim, **record warranty decision** (submit to OEM / return / reject) |
| `admin` | Manage knowledge documents, models catalogue, checklists, thresholds, users; verify audit chain. **Cannot decide claims.** |

**Row-level rules (enforced in repositories, not routes):**
- owner → only vehicles where `vehicle.owner_id == user.id`, and ROs/claims of those vehicles
- staff (`service_advisor`, `technician`, `warranty_admin`) → only ROs/claims where `ro.dealer_id == user.dealer_id`
- `admin` → configuration and audit only; no RO/claim decision endpoints
- A record the actor cannot see returns **404**, never 403, so its existence is not revealed.

## 4. Synthetic Domain Data (A3)

- Fictional OEM **"Veloxa Motors"**, WMI `VLX`. Models: **Veloxa Aria** (petrol hatchback), **Veloxa Terra**
  (diesel SUV), **Veloxa Volt** (battery-electric crossover). No real brands, no real customers, ever.
- Corpus in `data/knowledge/` (every page watermarked **SYNTHETIC — FOR DEMO ONLY**):
  `owner_manual_{model}.pdf`, `service_manual_{model}.pdf`, `warranty_booklet.pdf`, `tsb/*.pdf` (5–8),
  `recalls/*.pdf` (2–3), `dtc_reference.pdf`, `labour_time_guide.csv`, `parts_price_list.csv`.
  Markdown sources live in `data/knowledge/src/`. They are the **only** place domain numbers are authored.
- VIN: 17 chars, no I/O/Q, ISO 3779 check digit at position 9, WMI `VLX`. Validation is deterministic (`services/vin.py`).
- DTC meaning **always** comes from `dtc_reference.pdf` chunks. Not present → "code not found in reference".

## 6. State Machines (A5) — authoritative

**Repair Order**
```
DRAFT ─► BOOKED ─► CHECKED_IN ─► DIAGNOSING ─┬─► INFO_PENDING ─(docs/tests added)─► DIAGNOSING
                                             └─► ESTIMATE_READY ─► AWAITING_OWNER_APPROVAL
AWAITING_OWNER_APPROVAL ─┬─► APPROVED ─► IN_REPAIR ─► QUALITY_CHECK ─► READY_FOR_PICKUP ─► CLOSED
                         └─► DECLINED ─► READY_FOR_PICKUP
Any non-terminal state ─► CANCELLED (service_advisor only, reason required)
```
**Warranty Claim** (child of an RO)
```
DRAFT ─► PREPARED ─► WARRANTY_REVIEW_REQUIRED ─┬─► SUBMITTED_TO_OEM (DEMO adapter) ─► OEM_ACCEPTED | OEM_REJECTED
                                               ├─► RETURNED_FOR_INFO ─► PREPARED
                                               └─► REJECTED_BY_DEALER
```
- Transitions happen **only** in `app/services/state_machine.py::transition()`. It validates the transition table
  and the actor's role, then writes `*_status_history` and `audit_log` in **one DB transaction**.
- Terminal: RO `CLOSED`, `CANCELLED`. Claim `OEM_ACCEPTED`, `OEM_REJECTED`, `REJECTED_BY_DEALER`.
- The table is mirrored in code as data, not `if` chains. `docs/LLD.md` (Prompt 2) expands it.

**Who may trigger each transition** (resolved in P0-0b, decisions OD-02, OD-04, OD-05, OD-06)

| Machine | Transition | Actor |
|---|---|---|
| RO | DRAFT → BOOKED | owner (chat booking) or service_advisor |
| RO | BOOKED → CHECKED_IN | service_advisor |
| RO | CHECKED_IN → DIAGNOSING | technician (starts diagnosis) or service_advisor |
| RO | DIAGNOSING → INFO_PENDING | system (checklist gaps / unverified fields) or service_advisor |
| RO | INFO_PENDING → DIAGNOSING | system (re-check passes after upload/edit) or service_advisor |
| RO | DIAGNOSING → ESTIMATE_READY | system, only when the estimate is `estimable` |
| RO | ESTIMATE_READY → AWAITING_OWNER_APPROVAL | service_advisor ("send estimate"); the graph never sends it automatically |
| RO | AWAITING_OWNER_APPROVAL → APPROVED / DECLINED | owner, or service_advisor recording consent with a mandatory note. ≥ 1 customer-pay line approved → APPROVED; 0 → DECLINED. Line decisions are stored per line |
| RO | APPROVED → IN_REPAIR | service_advisor or technician |
| RO | IN_REPAIR → QUALITY_CHECK | technician |
| RO | QUALITY_CHECK → READY_FOR_PICKUP, DECLINED → READY_FOR_PICKUP, READY_FOR_PICKUP → CLOSED | service_advisor |
| RO | any non-terminal → CANCELLED | service_advisor, reason required |
| Claim | DRAFT → PREPARED | system (warranty + estimate + risk nodes done, checklist complete). Checklist gaps → stays DRAFT with gaps shown (the claim has no INFO_PENDING) |
| Claim | PREPARED → WARRANTY_REVIEW_REQUIRED | system (human_review node) |
| Claim | → SUBMITTED_TO_OEM / RETURNED_FOR_INFO / REJECTED_BY_DEALER | warranty_admin, rationale required |
| Claim | RETURNED_FOR_INFO → PREPARED | system after the requested info is added, or service_advisor |
| Claim | SUBMITTED_TO_OEM → OEM_ACCEPTED / OEM_REJECTED | DEMO OEM adapter (system actor) |

**Estimate vs. warranty ordering (OD-03):** the owner approves **customer-pay** lines only. Warranty and recall lines go to the
claim / recall flow in parallel, and the owner sees them as "pending warranty review" (never as "free" or "covered").
If a claim is later rejected, those lines come back to the owner as a new customer-pay approval request.

## 7. Deterministic Rules & Detectors (A6) — `autoserve-server/config/rules.yaml`

**Warranty** (`rules/warranty.py`): basic coverage years/km (whichever first); powertrain longer; EV battery longer
plus a capacity threshold. Exclusions: wear items, accident damage, aftermarket modification, missed scheduled
maintenance beyond tolerance. **Every number comes from `warranty_booklet.pdf`** and is mirrored in `rules.yaml`
with a `source_chunk_id`. Each finding is `{rule_id, result: pass|fail|unknown, inputs, source_chunk_id}`.
Missing input → `unknown`, never guessed.

**Detectors** (`rules/detectors.py`). Output is always an *"indicator for review"* with evidence:
| ID | Detector |
|---|---|
| D-01 | Odometer lower than a previous record (rollback indicator) |
| D-02 | Duplicate claim: same VIN + part within 90 days |
| D-03 | Repeat repair: same op code within 30 days |
| D-04 | Labour claimed > flat-rate × tolerance |
| D-05 | Part on claim not on invoice |
| D-06 | Invoice total ≠ Σ lines |
| D-07 | Repair date before vehicle in-service date |
| D-08 | Claim on a part covered by an open recall (should be a recall job) |
| D-09 | Prompt-injection-like content in an uploaded document (`prompt_injection_suspected`) |

Windows (90/30 days) and tolerances live in `rules.yaml`, never in code.

## 10. Forbidden Patterns (A9)

| ❌ Forbidden | ✅ Instead |
|---|---|
| LLM output written straight to the DB | Pydantic schema → service → repository |
| LLM decides status transitions, eligibility, hours, or amounts | `state_machine.transition()`, `rules/warranty.py`, `rules/calculator.py` |
| Specs, torque values, DTC meanings, labour times typed into prompts/code/tests | Retrieve from `data/knowledge/` and cite chunk ids (tests load fixtures from the corpus) |
| Calling an LLM client (`ChatOpenAI`, provider SDKs) directly in a node | `LLMService` (tokens, cost, latency, model logged to `llm_usage`) |
| Uploaded document text placed in the system prompt | `<untrusted_document>` in the user turn; extractor has no tools |
| LLM with SQL access | Allow-listed, role-scoped tools in `graph/tools/` |
| Query without ownership / dealer filter | Repositories require `actor` and apply the filter |
| Logging raw PII (name, phone, email, address, plate, full VIN) | `mask_pii()` in the structlog processor (VIN → last 6 only) |
| "Fraud detected", "AI approved warranty", "safe to drive" | "Indicator for review", "Preliminary assessment", "Stop safely and contact service" |
| `UPDATE`/`DELETE` on `audit_log` | Append-only + DB trigger + hash chain |
| "Tests pass" without running them | Run them; show the output |
| Unbounded retries / no timeouts | `max_retries=2`, timeouts from config |
| Money as `float` | `Decimal`, quantised with an explicit rounding mode |
| Unlabelled mock integration | Every mock (OEM portal, SMS/email, DMS, telematics, AV scan) named `Demo*` and labelled **DEMO** in UI + logs |

## 12. Definition of Done (every task)

1. Code follows the relevant `rules/*.md` and its `specs/` contract.
2. Tests written **and run**. The real output is pasted in the response, and all are green.
3. `ruff check`, `ruff format --check`, `mypy`, `eslint`, `tsc --noEmit` are clean for touched code.
4. No A1 / A9 violation. AI-facing text was checked against `rules/55-automotive-safety.md`.
5. New state changes go through `transition()` and write `audit_log`.
6. New queries go through repositories with the actor filter, and a security test covers the new route.
7. Any new number (coverage, tolerance, threshold) lives in config with a `source_chunk_id` or an ADR.
8. `TASK_TRACKER.md` row updated (status + evidence). `MEMORY.md` updated if the lesson is non-obvious.
9. Docs/specs updated if a contract changed. An accepted ADR is superseded, never edited.

## 13. Security Summary

- **AuthN:** DEMO JWT (HS256, short TTL, local only) → prod OIDC (Cognito, JWKS-verified RS256). Algorithm pinned; `none` rejected.
- **AuthZ:** `require_role()` dependency on every route, plus actor-scoped repositories (ownership / dealer). 404 on out-of-scope.
- **PII:** owner name, phone, email, address, plate, full VIN, location. Masked in logs (`mask_pii`), never in prompts unless needed, never in eval reports.
- **Uploads:** PDF/JPG/PNG allow-list, magic bytes, ≤ 10 MB, ≤ 20 pages, metadata stripped, images re-encoded, SSE storage, sha256, DEMO AV hook.
- **Prompt injection:** untrusted text is wrapped in `<untrusted_document>`/`<untrusted_user_input>`; extractors have no tools; outputs are schema-validated; D-09 flag.
- **LLM tools:** allow-listed, role-scoped, read-only unless the tool is an explicit, audited state-change request routed through `transition()`.
- **Audit:** `audit_log` is append-only, sha256 hash-chained, DB trigger blocks UPDATE/DELETE; `verify_chain()` admin endpoint.
- **Secrets:** env / Secrets Manager only. `.env` is never read by agents or committed.
- **Supply chain:** pinned deps (`uv.lock`, `package-lock.json`), bandit, pip-audit, npm audit in CI.
